# 余火·留声 — 产品需求文档（PRD）

> **版本**：v1.0 MVP  
> **日期**：2026-07-30  
> **定位**：时光胶囊式内容投递平台 — 让人在此刻留下想说的，在未来某个时刻送达  

---

## 一、产品概述

### 1.1 产品名称
**余火·留声**（Embers & Echoes）

### 1.2 一句话描述
用户上传文字/录音/影像，设定触发时间和收件人，系统在指定时刻将内容通过邮件投递给对方。

### 1.3 核心价值
- **情感价值**：为每个人提供"跨越时间的表达"能力
- **仪式感**：让告别、祝福、回忆有处安放、有期可达
- **安全感**：加密存储、用户可控、随时可撤

### 1.4 MVP 目标
跑通核心闭环：**注册 → 上传内容 → 设置投递 → 触发 → 邮件发送 → 状态追踪**

## 二、用户画像

| 画像 | 场景 | 核心诉求 |
|------|------|----------|
| 情感表达者 | 给未来的自己/爱人写一封信 | 定时投递，情感留存 |
| 临终关怀者 | 提前录制给家人的话 | 离世后触发，庄重送达 |
| 仪式创造者 | 生日/纪念日/毕业的定时祝福 | 固定日期触发，仪式感 |
| 故事记录者 | 记录自己的故事，愿意公开分享 | 匿名公开展示（后期） |

## 四、技术方案

### 4.1 架构概览

```
┌─────────────────────────────────────────────────┐
│                   H5 前端                        │
│         (HTML/CSS/JS, 移动端优先)                 │
└────────────────────┬────────────────────────────┘
                     │ HTTP/REST API
┌────────────────────┴────────────────────────────┐
│              Express.js 后端                     │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐  │
│  │ Auth │ │Content│ │Delivery│ │Trigger│ │Admin │  │
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘  │
│  ┌──────────────────────────────────────────┐   │
│  │  Services: Email / Crypto / Scheduler    │   │
│  └──────────────────────────────────────────┘   │
└──────┬───────────────────────────────┬──────────┘
       │                               │
┌──────┴──────┐               ┌───────┴───────┐
│   SQLite    │               │  文件存储      │
│   数据库     │               │  (加密上传)    │
└─────────────┘               └───────────────┘
```

### 4.2 技术栈

| 层 | 技术 | 说明 |
|----|------|------|
| 前端 | HTML5 + CSS3 + Vanilla JS | 移动端优先，无需构建 |
| UI 框架 | 自定义 CSS | 温暖色系，卡片式布局 |
| 后端 | Node.js + Express | RESTful API |
| 数据库 | SQLite (better-sqlite3) | 轻量，零配置，MVP 够用 |
| 认证 | JWT (jsonwebtoken) | 无状态鉴权 |
| 密码 | bcrypt | 哈希存储 |
| 邮件 | Nodemailer | SMTP 发送 |
| 加密 | Node.js crypto | AES-256 内容加密 |
| 定时 | node-cron | 定时触发器 |
| 文件 | Multer | 上传处理 |

### 4.3 H5 → 小程序演进路线

```
阶段1 (当前): H5 网页版 → 验证核心闭环
阶段2: 用 uni-app/Taro 重写前端 → 编译小程序
阶段3: 后端不变，小程序调用同一套 API
```

后端 API 设计为前后端分离，H5 和小程序共用同一套接口，切换前端时后端零改动。

## 九、风险与注意事项

1. **法律合规**：涉及用户敏感内容存储，需完善隐私政策和服务协议
2. **数据安全**：MVP 使用 AES 加密，生产环境需增加多层备份
3. **触发可靠性**：定时触发需考虑服务器重启、时区等问题
4. **邮件送达率**：免费 SMTP 有发送限制，生产环境建议用专业邮件服务
5. **内容审核**：H5 版免审核，但上线小程序时需配置内容安全检测

## 十、产品愿景扩展（来自用户构思文档，2026-07-30）

> 以下为产品早期构思中的扩展方向，用于指导中后期迭代，不要求 MVP 实现。

### 10.1 定位再校准
- **不是信托/银行，是"表达与交还"**；不碰财产，只走叙事。
- **不是宣发，是交还**——平台主动把内容发送给目标对象（像快递公司），而非对方来领，从根源规避冒领与诈骗质疑。

### 10.2 触发模型（中期/后期）
- 主动发送为主 + 死亡触发为主 + 亲友/医生/法医作替补执行链 + 发送前多重验证。
- MVP 的"手动/客服触发"即初期发令枪；真实死亡核验在国情下难自动化，靠人联系最务实。

### 10.3 媒介与实物交付（收费依据）
- 纸/物件的"线性、平面、弯曲、折叠"记忆价值 = 实物交付情感内核。
- **电子内容免费，实物信件/物品交付收费**；实物交付走民营快递"物品/纪念品寄递"或 EMS，规避邮政专营。

### 10.4 周期运营
- 每 5 年提醒用户更新内容；临近到期提醒频率递增（长期托管命脉，年费逻辑来源）。

### 10.5 内容治理与价值放大
- 安全池/敏感池隔离 + 匿名公开（公益价值）+ 改编分成（合同写明收益分配）。

### 10.6 社会网络（远期）
- 志愿者配送、脱口秀式倾诉舞台、公益展馆、养老院/临终关怀 B 端合作。

### 10.7 试水期商业化
- 以**个人收款码打赏/众筹**方式验证付费意愿（自愿支持，不承诺对价），不做经营性收费；正式收费再做个体户 + ICP 经营许可证 + 微信/支付宝商户号。
